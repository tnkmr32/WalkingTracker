## 前提

- アプリは[release-build-procedure.md](release-build-procedure.md)の手順でビルド・インストール済みであること
- 各テストケース実施後、結果は[verification-results.md](verification-results.md)に追記する
- Logcatは以下のコマンドで取得する（`GpsTrackingService.kt`が`"GpsPoc"`タグで出力）

```bash
adb logcat -s "GpsPoc:*"
```

- TC-04・TC-05のようにPC接続なし・屋外での実施が前提のテストケースでは、Logcatのリアルタイム監視の代わりに、記録開始ごとに端末側へ出力されるCSVログファイル（`Android/data/com.example.walkingtracker/files/gps_poc_log_<開始日時>.csv`、内容はLogcatと同一）を検証終了後に`adb pull`で回収して解析する（詳細は[release-build-procedure.md](release-build-procedure.md)「7.5. PC接続なしで屋外検証する場合」参照）
- 機種・Androidバージョンが異なる複数端末がある場合、テストケースごとに端末を明記して個別に実施・記録する

## TC-01: GPS取得の安定性（画面ON・フォアグラウンド）

- **目的**：画面ON・アプリをフォアグラウンドで開いたままの状態で、10秒間隔のGPS取得が安定して継続するかを確認する
- **事前条件**：屋外、GPS取得に問題ない見通しの良い場所

### 手順

1. アプリを起動し、位置情報等の権限をすべて許可する
2. `adb logcat -s "GpsPoc:*"` を実行し、ログ出力を待機する
3. 「記録開始」ボタンを押す
4. アプリを閉じずに画面をONのまま10分間放置する（他操作をしない）
5. 「記録停止」ボタンを押し、ログを停止する

### 期待結果 / 合格基準

- `point ...` ログが約10秒間隔で出力され続ける
- `gap=` の値が8〜12秒（10秒±2秒）に収まる割合が全体の95%以上
- `delayed=true` の件数が全体の5%未満

### 記録方法

- 取得件数・`delayed=true`件数・最大gap値を[verification-results.md](verification-results.md)に記録する
- 判定基準を外れる場合は課題として記載する（[verification-results.md](verification-results.md)の課題1参照）

## TC-02: GPS取得の安定性（画面OFF・ロック状態）

- **目的**：画面OFF・端末ロック状態でもForegroundServiceによりGPS取得が中断なく継続するかを確認する
- **事前条件**：屋外、TC-01と同条件の場所

### 手順

1. アプリを起動し、「記録開始」ボタンを押す
2. 常駐通知（「GPS取得PoC 記録中」）が表示されていることを確認する
3. 端末の電源ボタンを押して画面をOFF・ロックする
4. 10分間その状態を維持する（触らない）
5. 画面をONにしてロックを解除し、アプリを開く
6. 「記録停止」ボタンを押す

### 期待結果 / 合格基準

- 画面OFF中も`point ...`ログが約10秒間隔で出力され続ける（`adb logcat`はPC側で取得し続けるため画面OFFでも記録可能）
- 60秒以上の取得中断（`gap`が60秒以上）が発生しない（`GpsTrackingService.kt`の`INTERRUPTION_THRESHOLD_SECONDS`に該当するログ「◯秒以上の中断を検知」が出ないこと）
- 画面ロック解除後もアプリがクラッシュせず、記録状態（記録中）が保持されている

### 記録方法

- 画面OFF区間の開始・終了時刻と、その間の最大gapを記録する
- 中断検知ログが出た場合はその内容・時刻を課題として記載する

### 実施上の注意

- 常駐通知の表示継続、画面ロック解除後のクラッシュ有無、記録状態（記録中）が保持されているかは、CSVログの列（`timestamp,lat,lng,accuracy_m,gap_s,delayed,battery_percent`）には含まれないため、CSV解析だけでは判定できない。Logcatのリアルタイム監視または実施者の目視確認で判定する
- 本テストケースはPC接続・Logcatリアルタイム監視での実施を前提とする。CSVでの事後解析に代替しないこと

## TC-03: GPS取得の安定性（他アプリ使用中・バックグラウンド）

- **目的**：本アプリをバックグラウンドに回し、他アプリを操作している間もGPS取得が継続するかを確認する
- **事前条件**：屋外、TC-01と同条件の場所

### 手順

1. アプリを起動し、「記録開始」ボタンを押す
2. ホームボタン等で別アプリ（例：ブラウザ、地図アプリ等）を起動し、10分間操作を続ける（本アプリはバックグラウンドのまま）
3. 本アプリに戻り、「記録停止」ボタンを押す

### 期待結果 / 合格基準

- バックグラウンド中も`point ...`ログが約10秒間隔で出力され続ける
- 60秒以上の中断が発生しない
- 常駐通知が他アプリ操作中も表示され続けている

### 記録方法

- TC-02と同様に開始・終了時刻、最大gapを記録する

### 実施上の注意

- 常駐通知が他アプリ操作中も表示され続けているかは、CSVログの列には含まれないため、CSV解析だけでは判定できない。操作中に実施者が目視で確認する
- 本テストケースはPC接続・Logcatリアルタイム監視での実施を前提とする。CSVでの事後解析に代替しないこと

## TC-04: Dozeモード長時間放置時の継続性

- **目的**：画面OFFのまま長時間放置し、DozeモードやメーカーごとのバックグラウンドアプリKill機構によってServiceが停止させられないかを確認する
- **事前条件**：屋外、または少なくとも屋内でGPSが入る場所。端末をUSB給電なしの状態にする（USB接続中は端末によってDozeに入らない場合があるため）

### 手順

1. アプリを起動し、「記録開始」ボタンを押す
2. USBケーブルを抜き、端末を画面OFF・ロック状態にし、動かさずに30分以上放置する
3. 放置後、画面をONにしてアプリの状態を確認する
4. 「記録停止」ボタンを押す
5. USB再接続し、`adb pull`でCSVログファイルを回収する（[release-build-procedure.md](release-build-procedure.md)「7.5」参照）

### 期待結果 / 合格基準

- 放置時間中も10秒間隔でのGPS取得が継続する
- 60秒以上の中断が発生しない
- 端末のメーカー独自の電池最適化機能（例：一部メーカーの「スリープ状態のアプリ」等）によってアプリが強制終了・通知が消える等の事象が発生しない

### 記録方法

- 放置前後の記録件数・累積取得件数の差分から、放置中も想定件数（放置時間÷10秒）に近い件数が記録されているか確認する
- Service停止・強制終了が疑われる場合、端末側の「バッテリー使用状況」「最近終了したアプリ」等の設定画面も確認し、結果に記載する

### 実施上の注意

- CSVログの記録件数だけでは、放置中に単に記録が完走しなかったのか、メーカー独自の電池最適化機能によりアプリが強制終了・通知消失したのかを区別できない場合がある。放置後は画面表示・常駐通知の状態を必ず目視確認し、件数不足や中断を検知した場合は端末側の「バッテリー使用状況」「最近終了したアプリ」等の設定画面も併せて確認する

## TC-05: バッテリー消費率（12時間換算）

- **目的**：一定時間記録を継続した際のバッテリー消費から、12時間あたりの消費率を推計し10%以内に収まるか確認する
- **事前条件**：端末を満充電（または任意の一定%）から開始し、USB給電なしで実施する（PC接続・Wi-Fi ADBも充電・行動範囲の制約になるため行わない）

### 手順

1. 端末のバッテリー残量を記録する（開始時%）
2. アプリを起動し、「記録開始」ボタンを押す
3. USBケーブルを抜き、最低1時間以上（推計精度を上げるためできれば2〜3時間）、画面OFF・バックグラウンドを中心とした状態で記録を継続する（屋外歩行を含めてよい）
4. 記録終了後、バッテリー残量を記録する（終了時%）
5. 「記録停止」ボタンを押す
6. USB再接続し、`adb pull`でCSVログファイルを回収する（[release-build-procedure.md](release-build-procedure.md)「7.5」参照）。ログ中の`battery_percent`列も開始時・終了時%との突合に使う

### 期待結果 / 合格基準

- 消費率(%) ÷ 記録時間(h) × 12h で算出した12時間換算消費率が10%以内

### 記録方法

- 開始時%・終了時%・経過時間・算出した12時間換算消費率を[verification-results.md](verification-results.md)に記録する
- アプリ内の「バッテリー: 開始時◯% → 現在◯%」表示、またはLog中の`battery=`値も突合の参考にする

## TC-06: GPS精度（屋外実測）

- **目的**：屋外歩行時のGPS取得精度（accuracy）が想定値（概ね5〜15m）から乖離していないか確認する
- **事前条件**：見通しの良い屋外（高層ビル街・トンネル・屋根付き通路等は避ける）

### 手順

1. アプリを起動し、「記録開始」ボタンを押す
2. 屋外を10分以上実際に歩行しながら記録する
3. 「記録停止」ボタンを押す
4. Logcatまたは画面上の一覧から各取得点の`accuracy`値を確認する

### 期待結果 / 合格基準

- 大半の取得点でaccuracy値が概ね5〜15mの範囲に収まる
- 高層ビル街やトンネル等、GPS精度が悪化しやすい環境下での値も参考値として記録する（合否判定は見通しの良い屋外での値を基準とする）

### 記録方法

- 全取得点のaccuracy値の分布（最小・最大・平均値の目安）を記録する
- 歩行場所の環境（周辺の建物状況等）も記録に残す

## TC-07: 記録中の位置情報権限剥奪検知

- **目的**：記録中に端末の「設定」からアプリの位置情報権限を剥奪した際、アプリが検知して記録を停止するまでの挙動を確認する
- **事前条件**：なし（屋内でも実施可）
- **背景（2026-09-23実機検証で判明・改訂）**：フォアグラウンドサービスが使用中の`ACCESS_FINE_LOCATION`を「設定」から剥奪すると、Android OSがアプリのプロセスごと強制終了することを実機（[verification-results-20260922_163720.md](verification-results-20260922_163720.md) 課題3）で確認済み。プロセスが終了した時点でそのプロセス内のコード（ポーリングによる検知処理を含む）は一切実行できないため、当初想定していた「5秒以内のリアルタイム検知」は本シナリオでは原理的に成立しない。検知経路は[background-tracking.md 権限の検知手段](../../02-architecture-design/background-tracking.md)の経路A（プロセス生存時のポーリング、まれ）・経路B（起動時の未確定セッション検出、実機で確認された主経路）に改訂されている。本テストケースの合格基準もそれに合わせて改訂した

### 手順

1. アプリを起動し、「記録開始」ボタンを押す
2. 数回GPS取得ログが出力されることを確認する
3. ストップウォッチ等で時刻を記録しつつ、端末の「設定」→「アプリ」→本アプリ→「権限」から位置情報の許可を取り消す
4. Logcatを監視し、以下のいずれの経路で停止するかを確認する
   - 経路A：プロセスが生存し続け、Logcatに`ACCESS_FINE_LOCATION剥奪を検知`ログが出力される
   - 経路B：プロセスが強制終了され（Logcat上でPIDが変化する）、`START_STICKY`によるサービス再起動後に`ACCESS_FINE_LOCATION未許可のため開始を中止`ログが出力される（前回セッションが記録中のまま終了していた場合、権限剥奪と推定した旨のログも併せて出力される）
5. アプリを（手動で、または自動再起動後に）開き、画面に権限剥奪の警告が表示されることを確認する

### 期待結果 / 合格基準

- 経路A（プロセス生存）の場合：権限剥奪操作から次回のGPS取得ループ（最大10秒後）以内に検知される
- 経路B（プロセスキルを伴う場合、実機での主要ケース）の場合：`START_STICKY`によるサービス再起動、またはユーザーが次回アプリを開いたタイミングのいずれか早い方で、権限剥奪による中断であったと判定される（即時性は問わない）
- いずれの経路でも、アプリの記録状態が自動的に「停止中」に変わり、（経路Bの場合は次回起動時に）画面に権限剥奪の警告が表示される
- 記録開始からプロセスキルまでに取得できていたデータ（CSVログ・本実装ではTrackPoint）は破棄されず、最後の取得時刻まで確定保存される

### 記録方法

- どちらの経路で停止したか（Logcat上のPID変化の有無）を記録する
- 経路Aの場合：権限剥奪操作の時刻と検知ログの時刻の差分を記録する
- 経路Bの場合：プロセスキルからサービス再起動までの時間（参考値）と、アプリ再起動後に警告が正しく表示されたかを記録する

### 実施上の注意

- 権限剥奪の検知ログ（`ACCESS_FINE_LOCATION剥奪を検知`）は、`stopTracking()`によるCSVクローズ後に出力されるためCSVログには書き込まれない（`GpsTrackingService.kt`参照）。検知時刻・経路の判定にはLogcat（`adb logcat -s "GpsPoc:*"`）のリアルタイム監視が必須であり、CSV解析のみでは判定できない（CSVからは「最後の取得時刻でログが途切れている」ことまでしか分からない）
- 本テストケースはPC接続・Logcatリアルタイム監視での実施を前提とする。CSVでの事後解析に代替しないこと

## TC-08: FOREGROUND_SERVICE_LOCATION宣言のみでのサービス起動・継続

- **目的**：`AndroidManifest.xml`の`FOREGROUND_SERVICE_LOCATION`宣言のみで、Android 14以降でもForegroundServiceの起動・継続に追加の制約なく成功するかを確認する
- **事前条件**：Android 14（API 34）以降の端末を用意する

### 手順

1. 対象端末のAndroidバージョンを確認する（設定 → デバイス情報）
2. アプリを起動し、「記録開始」ボタンを押す
3. Logcatまたは画面上でServiceが正常に起動し、GPS取得が開始されることを確認する
4. TC-01〜TC-04のいずれかの条件（画面ON/OFF等）で10分程度継続させ、途中でServiceが強制停止されないか確認する

### 期待結果 / 合格基準

- マニフェスト宣言（`FOREGROUND_SERVICE_LOCATION`）のみでServiceが起動し、`SecurityException`等のエラーが発生しない
- Android 14以降特有の追加制約（例：起動元のアプリ状態に関するエラー等）が発生せず、継続してGPS取得が行える

### 記録方法

- 端末のAndroidバージョンを必ず記録する
- エラーが発生した場合はスタックトレース全文を記録する

### 実施上の注意

- 端末のAndroidバージョンや`SecurityException`等のエラー内容・スタックトレースはCSVログの列には含まれないため、CSV解析だけでは判定できない。Logcat（`adb logcat -s "GpsPoc:*"`）の監視と、端末の「設定」→「デバイス情報」の確認を必ず実施する
- CSVログの記録が完走していても、Service起動時の制約エラー（起動元アプリ状態に起因するエラー等）が別途発生していないとは限らないため、Logcat確認を省略しないこと
